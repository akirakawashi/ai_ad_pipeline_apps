# План реализации: геозоны и коэффициент значимости β

**Статус:** согласовано, к реализации. Обновлено 24 июля 2026.
**Что делаем:** вводим геозоны и коэффициент значимости места β — множитель,
который сейчас стоит заглушкой `1.0`. Реализация «по времени», без GPS.

---

## Идея в двух абзацах

Камера включается в момент старта (принято), значит начало видео = точка A
маршрута, конец = точка B. Поэтому **доля времени видео ≈ доля пути**: на середине
видео машина в географической середине маршрута. Это позволяет размечать участки
маршрута в долях от длительности, не имея GPS.

Геозона — участок маршрута с коэффициентом значимости. Центр города дороже
окраины → выше коэффициент. Объект попадает в зону по своему времени, зона даёт β,
β входит в итоговый балл. Погрешность от локальных пробок бизнес принял осознанно.

---

## Ключевые решения (все, что согласовали)

| Тема | Решение |
|---|---|
| Привязка зоны | по времени (доля 0…1 от длительности видео), не по координатам |
| Модель зоны | **интервалы**: начало + конец + коэффициент; неразмеченное = β 1.0 |
| Дефолт | вне размеченных зон β = 1.0 (умножение на 1 ничего не меняет) |
| Шкала | 1.0 нейтрально, > 1 важнее, < 1 слабее |
| Область зоны | локальна для маршрута |
| Разметка | кликами на плеере съёмки: «отсюда начинается зона X, коэффициент Y» |
| Туда/обратно | два разных маршрута, у каждого своя разметка |
| Где считается β | на бэкенде, на лету при запросе; пайплайн про β не знает |
| Позиция объекта | по `best_timestamp` — момент лучшего кадра |
| Overlay | карточка на видео = физика (S·α); β только в метриках и графиках |
| Пересчёт | бесплатный: сменил зоны → следующий запрос свежий |
| Справочник объектов | геозоны его не ждут; список объектов в зоне — визуальный |

**Почему интервалы, а не смежные границы.** Размечаешь только важные куски (центр),
остальное само нейтрально (β = 1) — «дыры» это фича: не надо явно размечать всю
трассу. Так человек и думает: «центр начался тут, закончился тут» = два клика.
Единственная цена — интервалы могут пересечься; пересечения запрещаем валидацией,
дыры разрешаем.

**Почему β на бэкенде.** β зависит от зон, а зоны размечают *после* обработки видео
и *меняют* когда угодно. Нет момента «β финальный». Значит β нельзя зашивать ни в
пайплайне, ни в артефактах — он живёт и пересчитывается. Считаем на лету из
`timestamp` (он уже в CSV) + текущих зон.

---

## Модель данных

Одна таблица (зоны локальны для маршрута, отдельная привязка не нужна):

```
route_geozones
  route_geozones_id   PK
  routes_id           FK → routes (CASCADE), индекс
  name                строка ("Центр", "Город")
  start_fraction      доля 0.0…1.0 — начало участка
  end_fraction        доля 0.0…1.0 — конец участка
  coefficient         множитель β (float)
  created_at / updated_at
```

**Семантика интервалов.** Каждая строка — самостоятельный участок [начало, конец]
с коэффициентом. Участки на маршруте **не пересекаются** (валидация при создании).
Дыры между ними разрешены — там β = 1.0 по умолчанию.

```
0.35 … 0.55  "Город"   1.2     → на этом отрезке β = 1.2
0.55 … 0.70  "Центр"   1.5     → β = 1.5
(0.00…0.35 и 0.70…1.00 не размечены → β = 1.0)
```

Валидация: `0 ≤ start < end ≤ 1`; новый интервал не налезает на существующие
этого маршрута.

> Миграцию пишет владелец сам, после готовности кода.

## Этапы работ

### Этап 1. Модель `route_geozones`
`models.py`: таблица + связь `Route.geozones`. `GeozoneDTO`. Только структура.

### Этап 2. CRUD геозон (бэкенд)
- `GET    /api/v1/cities/{c}/routes/{r}/geozones` — границы маршрута;
- `POST   /api/v1/cities/{c}/routes/{r}/geozones` — добавить границу;
- `PATCH  /api/v1/geozones/{id}` — правка;
- `DELETE /api/v1/geozones/{id}` — удалить.

Репозиторий, сервис, роутер, DTO. Валидация: `0 ≤ доля ≤ 1`, коэффициент > 0,
дубль доли → 409 (общий обработчик IntegrityError уже есть).

### Этап 3. Расчёт β на бэкенде — ядро
Чистая функция:
```
beta(fraction, intervals) -> float
    найти интервал, где start ≤ fraction < end;
    вернуть его coefficient; если ни один не подходит — 1.0
    (пересечений нет по валидации, значит совпадение не более одного)
```
Позиция объекта — **`best_timestamp_sec` / `duration_sec`**. Лучший кадр = момент,
когда машина ближе всего к щиту, то есть щит вернее всего в своей зоне. Готовое
поле, считать ничего не надо.

`pipeline_run_service.get_summary` переписывается: источник — `TRACKS`, а не
`BRAND_SUMMARY`. Для каждого объекта: доля → `beta` → `V = S·α·β`, затем сумма по
брендам. `get_objects` применяет β при сортировке и выдаче.

Зоны — по маршруту съёмки: `run → assignment → route → geozones`. Съёмка «без
задания» → маршрута нет → β = 1 у всех объектов.

**Бэкенд перестаёт читать `visibility_value` из CSV** — считает V сам из
`attention_seconds` (S) и `confidence_coef` (α), которые в CSV остаются. Это
снимает зависимость от «недо-итога» с β = 1.

### Этап 4. Разметка кликами (фронтенд) — основной UI
На странице съёмки, поверх `VideoOverlayPlayer` (он даёт `currentTime` и
`duration`):
- отмечаешь начало и конец участка (две кнопки «начало здесь» / «конец здесь»,
  каждая берёт `currentTime / duration`), затем имя зоны + коэффициент;
- список интервалов маршрута, правка/удаление;
- при сохранении — проверка, что не пересекается с уже размеченными;
- подсказка: «размечаешь один раз на маршрут, применится ко всем его съёмкам».

Разметка — свойство **маршрута**, съёмка лишь холст. Порядок: сначала хотя бы одна
съёмка, потом разметка (без видео кликать не по чему).

### Этап 5. Показ зон и β (фронтенд)
- полосы зон на таймлайне плеера (подпись + коэффициент);
- в метриках заметности значение теперь с β — приходит готовым из этапа 3.

### Этап 6. Уборка пайплайна — к чистоте, не блокирует β
После того как бэкенд перестал зависеть от `visibility_value`, в пайплайне это
мёртвый груз (S·α с β = 1). Убираем:
- `significance_coef` — поле-заглушка, снаружи никто не читает;
- `visibility_value` — из `TrackCsvRow` и `aggregation.py`;
- автономные отчёты пайплайна (`html_report`, `charts`) — переводим на базовую
  заметность S·α (они про качество детекции, не про бизнес-метрику);
- overlay остаётся как есть: карточка = физика S·α.

Не блокирует функцию — β работает и с оставшимся мёртвым полем. Это гигиена.

### Этап 7. Тесты (сквозь все этапы)
- `beta`: пустой список → 1.0; доля в дыре → 1.0; доля внутри интервала; ровно на
  краях (`start` включается, `end` нет); до всех и после всех интервалов;
- интеграция: съёмка с зонами → `get_summary` даёт V с β; сменил зону → V меняется
  без перепрогона; съёмка без задания → β = 1;
- расширяем существующий `tests/` (conftest с временной БД готов).

## Тонкости — человеческим языком

**Почему `best_timestamp`, а не появление или середина.** Щит виден несколько
секунд: появился вдали (маленький), проехали мимо (крупный), ушёл из кадра. Для
зоны нужна одна точка во времени. Момент *появления* смещает щит назад — его видно
издалека, когда машина ещё в прошлой зоне. *Лучший кадр* — когда щит максимально
крупный, то есть машина ближе всего к нему → вернее его настоящая зона. И это
готовое поле, считать середину не нужно.

**Почему туда/обратно — два маршрута.** Едем «туда»: центр проезжаем на 30%
времени. Едем «обратно» (та же дорога с другого конца): центр теперь на 70%.
Зеркально. Одна разметка обоим не подходит. Решение — «Проспект-туда» и
«Проспект-обратно» как отдельные маршруты, у каждого своя разметка. Раз зоны и так
локальны для маршрута — это ничего не стоит.

**Почему β по объекту, а не «в интеграле».** Можно считать β отдельно для каждого
кадра щита и усреднять — точнее на границах зон, но дороже (покадровый проход) и
почти без выигрыша: щит виден 2–5 с, почти всегда в одной зоне. Берём один β на
объект по его лучшему кадру.

**Почему overlay = физика.** Карточка поверх кадра показывает «сколько внимания
щит забрал в этом кадре» (размер, близость, контраст). Ценность *места* (β) —
бизнес-слой, ему место в рейтингах и сводках, не на карточке момента. Поэтому
overlay не пересчитываем; аннотированное видео β не касается вообще (там нет числа
заметности). *Если позже захотим β и на карточках — бэкенд наложит его при отдаче
overlay на лету; недорого, но пока не делаем.*

**Свёртки задания и маршрута.** Получают β бесплатно: они не считают заметность
сами, а зовут `get_summary` каждой съёмки. Раз он теперь с β — и задание, и
маршрут наследуют β без отдельной работы.

**Производительность.** Уровень маршрута начнёт читать `tracks.csv` многих съёмок.
`tracks` мал (объекты, не кадры) — на десятках съёмок терпимо. Станет узко — кэш /
снимки показателей (сейчас в беклоге, вместе с DWH).

## Порядок и зависимости

```
Этап 1 (модель) → Этап 2 (CRUD) → Этап 3 (β на бэке) → рабочий β
                                         ↓
                      Этап 4 (разметка) → Этап 5 (показ)
                                         ↓
                  Этап 6 (уборка пайплайна — можно отложить)
                  Этап 7 (тесты — по ходу каждого этапа)
```

Этапы 1–3 дают работающий β: зоны заводятся хоть напрямую в базу, эффект виден на
метрике. Этап 4 — разметка сверху. Этап 6 не блокирует функцию, это гигиена.

**Грубая оценка:** модель + CRUD ~1 день; β на бэке ~1–2 дня (главное — аккуратно
переписать `get_summary`); разметка на фронте ~2 дня; показ + тесты ~1 день;
уборка пайплайна ~полдня. Итого порядка недели.
