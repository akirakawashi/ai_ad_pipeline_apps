## Что уже хорошо — не трогать

- **Бэкенд — честная чистая архитектура**: `domain / application / infrastructure / presentation`. Для проекта такого размера это редкость.
- **`pipeline_contracts` как явный общий контракт** — очень удачное решение. Благодаря ему переименование метрики прошло сквозь ML+бэк+фронт за один проход.
- **`.gitignore` дисциплинированный** — ни весов, ни выходов, ни датасетов в гите.
- **Worker спроектирован отдельным процессом** (`run_forever()`), а не фоновой задачей внутри API.
- **Пайплайн — чистая цепочка стадий** в `runner.py`; пакет `scoring/` разложен по одному фактору на файл.

---

## Решение: репозитории НЕ разделяем

Разделение на репозитории решало бы проблемы, которых у проекта нет, и усилило бы те, что есть.

**Аргумент из практики:** переименование полей метрики прошло сквозь ML → контракт → бэкенд → фронт **одним заходом** с проверкой `ruff` + `tsc` за минуту. В мультирепо это 3–4 согласованных PR, публикация новой версии `pipeline_contracts`, бампы зависимостей и окно рассинхрона. Ради 382 строк контракта — неоправданная цена.

**Пересмотреть решение, если появится хотя бы одно:**
- разные команды с разным темпом релизов;
- контракт нужен внешним потребителям (не только этому продукту);
- ML-часть уезжает в отдельный продукт.

> Нужно разделение **не по репозиториям, а по процессам и пакетам внутри монорепо** — даёт почти всю выгоду без боли мультирепо.

## Задачи по приоритету

### 1. 🔴 Нет тестов (0 штук)

Самая большая дыра. Крупный рефакторинг метрики проверялся временными скриптами, которые не сохранились. Следующий рефакторинг будет вслепую.

**Что делать:** завести `tests/` + pytest. Начать со `scoring/` — там чистые функции без зависимостей, тесты пишутся тривиально, ценность максимальная.

Минимальный набор для старта:
- площадь: границы бинов, интерполяция, монотонность;
- положение: точки кривой, своя > встречной, зеркалирование при `handedness="left"`;
- контраст: высокий / средний / сливается;
- уверенность: таблица α, пол 0.5;
- сквозной `I → S → V` через `fill_detection_scoring` + `build_tracks`.

Дальше — контракт (`pipeline_contracts`) и сервисы бэкенда.

### 2. 🔴 Worker не в деплое, API тащит весь ML

- `apps/backend/src/worker/main.py` существует, но **сервиса `worker` нет в `docker-compose.yml`** — его никто не поднимает.
- `apps/backend/src/worker/pipeline_worker.py` импортирует `run_pipeline` **в процессе бэкенда** → образ API обязан содержать `torch`, `ultralytics`, `easyocr`, `timm`.

**Последствия:** гигантский образ API, медленные сборки, невозможность масштабировать API отдельно от обработки, тяжёлая работа в процессе API-сервиса.

**Что делать:** добавить сервис `worker` в compose; разделить образы — `api` (лёгкий) и `worker` (с ML).

### 3. 🟠 Зависимости одной кучей

В `pyproject.toml` единый `dependencies`, где `fastapi` соседствует с `ultralytics` / `easyocr` / `timm` / `scikit-learn`. Группа `backend` есть, но основной список — объединение всего.

**Что делать:** uv workspaces или честные группы: `api` / `ml` / `worker = api + ml`. Следствие задачи №2, образ API похудеет в разы.

### 4. 🟠 Обучение и инференс в одном дереве

`ml/ad_detection` (4.1k строк) и `ml/classifier` (1.9k) — тренировочные скрипты и ноутбуки, в проде не нужны. `ml/pipeline` — продакшн-инференс. Лежат вперемешку.

**Что делать:** разнести на `ml/inference/` (прод) и `ml/training/` (research). Прод-образ тянет только inference.

### 5. 🟡 Мелкая уборка

- Пустая папка `scripts/` — удалить.
- Пять `.md` в корне (`README`, `ROUTES_ARCHITECTURE_PLAN`, `business-presentation`, `metric-implementation-plan`, `visibility-score-methodology`, этот файл) — перенести в `docs/`.
- Фронтенд не контейнеризован: нет `Dockerfile`, нет сервиса в compose.
- `sys.path`-бутстрап в `worker/main.py` — костыль; уйдёт сам после задачи №3.
- `__pycache__` в корне репозитория — следствие запуска из корня.
