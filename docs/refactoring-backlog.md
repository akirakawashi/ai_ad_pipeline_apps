## Что уже хорошо — не трогать

- **Бэкенд — честная чистая архитектура**: `domain / application / infrastructure / presentation`.
- **`pipeline_contracts` как явный общий контракт** — благодаря ему переименования метрики проходят
  сквозь ML + бэк + фронт за один заход.
- **`.gitignore` дисциплинированный** — ни весов, ни выходов, ни датасетов в гите.
- **Воркер спроектирован отдельным процессом** (`run_forever()`), а не фоновой задачей внутри API.
- **Пайплайн — чистая цепочка стадий** в `runner.py`; пакет `scoring/` разложен по одному фактору на
  файл.
- **Тесты появились** (задача из первой версии этого бэклога закрыта): 149 штук на расчёты, геозоны,
  свёртки, каталог, задания, съёмки, справочники.

## Решение: репозитории НЕ разделяем

Разделение на репозитории решало бы проблемы, которых у проекта нет, и усилило бы те, что есть.

**Аргумент из практики:** переименование полей метрики прошло сквозь ML → контракт → бэкенд → фронт
**одним заходом** с проверкой `ruff` + `tsc` за минуту. В мультирепо это 3–4 согласованных PR,
публикация новой версии `pipeline_contracts`, бампы зависимостей и окно рассинхрона. Ради 382 строк
контракта — неоправданная цена.

**Пересмотреть решение, если появится хотя бы одно:**
- разные команды с разным темпом релизов;
- контракт нужен внешним потребителям (не только этому продукту);
- ML-часть уезжает в отдельный продукт.

> Нужно разделение **не по репозиториям, а по процессам и пакетам внутри монорепо** — даёт почти всю
> выгоду без боли мультирепо.

## A. Долг вокруг метрики

Самая дорогая часть бэклога: продукт вокруг метрики построен, а сами числа не проверены на живом
материале.

### A1. 🔴 Новая метрика ни разу не считалась на реальном видео

Последний живой прогон (`outputs/pipeline/20260623_061943_VideoProject`) сделан **до** переделки
метрики и содержит старые колонки. Формулы `I = A·P·C`, `S = ΣI·Δt`, α и β проверены только юнит- и
интеграционными тестами.

**Что делать:** один проезд на GPU с текущими весами, затем посмотреть распределения A, P, C, α.

### A2. 🔴 Таблица площади рассчитана не на такую съёмку

Замер по сырым данным старого прогона (6 128 детекций): медианная площадь щита — **0.47 % кадра**,
99-й процентиль — 3.38 %, больше 5 % — одна детекция. При текущей таблице **52.6 % детекций упали бы
на пол `A = 0.30`**, то есть половина находок по площади не различается вообще.

**Что делать:** после A1 сдвинуть бины `AreaConfig` под реальное распределение. Числа правятся в
`ScoringConfig`, код не трогается.

### A3. 🟠 Контраст на реальном видео не считался ни разу

Единственный фактор, у которого нет даже старого замера: в прежнем прогоне его не было в артефактах.
Проверить можно только вместе с A1.

### A4. 🟠 Стабильность бренда по треку не влияет на α

`scoring/confidence.py` принимает `detections` и игнорирует их — α выводится только из
`final_brand_conf`. Заготовка есть, логики нет. Нужно решение: считать ли разброс бренда по трекам
частью уверенности.

### A5. 🟡 Единица `V` ни во что не переводится

`V` = секунды × безразмерные коэффициенты. «Процент заметности» на графиках — доля внутри одного
видео, абсолютной шкалы нет. Пока сравнения относительные, это не мешает; для внешней отчётности
понадобится нормировка.

## B. Деплой и зависимости

### B1. 🟠 API-образ тащит весь ML

`apps/backend/src/worker/pipeline_worker.py` импортирует `run_pipeline`, поэтому образ API обязан
содержать `torch`, `ultralytics`, `easyocr`, `timm`. Воркер при этом всё равно живёт на хосте: ему
нужен GPU.

**Что делать:** разделить образы — `api` (лёгкий) и `worker` (с ML); в compose добавить сервис
`worker` для машин, где GPU доступен контейнеру.

### B2. 🟠 Зависимости одной кучей

В `pyproject.toml` основной `dependencies` объединяет всё: `fastapi` рядом с `ultralytics` и
`easyocr`. Группа `backend` для образа API есть, но общий список остаётся свалкой.

**Что делать:** uv workspaces или честные группы `api` / `ml` / `worker = api + ml`. Следствие B1.

### B3. 🟡 Фронтенд не контейнеризован

Нет `Dockerfile`, нет сервиса в compose — только `pnpm dev`.

## C. Мелочи, которые чинятся за минуты

### C1. `run_video_pipeline.sh` передаёт несуществующий аргумент

Скрипт добавляет `--brand-overrides`, если существует `ml/pipeline/brand_overrides.csv`, а у
`run_pipeline.py` такого аргумента нет. Работает только потому, что файла нет: появится — скрипт
упадёт.

### C2. `README.md` устарел в части метрики

Раздел «Как проходит обработка видео» верен, всё про расчёт заметности — из прошлой версии системы.

### C3. Три сводных CSV пишутся и никем не читаются

`brand_summary_by_tracks.csv`, `brand_summary_by_detections.csv`, `frame_summary.csv`
регистрируются как артефакты, но бэкенд считает всё сам из `tracks.csv`. Единственный потребитель —
автономный `report.html` пайплайна. Либо оставить как есть и записать это как осознанное решение,
либо перестать регистрировать их в БД.

### C4. Старые ошибки статических проверок

Три `mypy` в бэкенде (`catalog_service.py`, `sql_catalog_repository.py`), около одиннадцати в тестах,
одна `eslint` — `set-state-in-effect` в `apps/frontend/src/pages/UploadPage.tsx:86`. Появились до
текущих работ, ни одна не мешает.

### C5. `__pycache__` в корне репозитория

Следствие запусков из корня. Косметика.

## D. Производительность (пока не болит)

Свёртки читают `tracks.csv` каждой готовой съёмки по запросу: задание — своих, маршрут — всех съёмок
всех своих заданий. Файлы маленькие (объекты, а не кадры), на десятках съёмок терпимо. Станет узко —
понадобится кэш посчитанных метрик; тогда же всплывёт вопрос, что делать с историей при правке
геозоны, потому что сегодня цифры пересчитываются на каждый запрос и правка зоны меняет прошлое.
