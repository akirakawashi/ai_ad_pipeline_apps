Бизнес-требования
1.	Требуется реализовать расчёт итоговой оценки видимости рекламной конструкции (Visibility Score) по видео, снятому на контролируемых точках замера.
2.	Оценка должна быть воспроизводимой и сопоставимой между замерами: одинаковая конструкция при одинаковых условиях съёмки получает одинаковую оценку.
3.	Расчёт разделяется на два независимых этапа:
a.	извлечение сырых метрик из видео (выполняется моделью один раз);
b.	агрегация метрик в итоговую оценку (выполняется отдельным модулем поверх сохранённых метрик).
4.	Пересчёт итоговой оценки при изменении коэффициента охвата выполняется без повторной обработки видео.
5.	Соотношение метрик качества показа (время, площадь, положение, контраст) фиксировано в системе и не настраивается пользователем.
6.	Коэффициент охвата (значимость точки замера по трафику): MVP — статические данные, предоставленные отделом маркетинга (заносятся в справочник точек замера; отдел маркетинга ими в системе не управляет); этап развития — динамическая оценка по трафику в кадре (автомобили, общественный транспорт, пешеходы).
7.	Требования к участникам процесса:
a.	Администратор: ведёт справочник точек замера и коэффициенты охвата (по данным отдела маркетинга); запускает обработку и пересчёт.
b.	Пользователь (аналитик/менеджер): просматривает результаты оценки, не влияет на формулу.
Функциональные требования
1.	Модель расчёта — гибридная мультипликативная:
Экспозиция E     =  время в кадре (сек) × балл(площадь в кадре)
QualityScore     =  E × K_положения × K_контраста
VisibilityScore  =  QualityScore × K_охвата

2.	Экспозиция (E) — накопительный эффект показа: произведение сырого времени в кадре (сек) и балла площади в кадре; шкала баллов для времени не применяется. Конструкция с большим временем, но малой площадью (и наоборот) получает низкую экспозицию — компенсация между этими метриками не предусмотрена намеренно.
3.	Модификаторы (K_положения, K_контраста) — понижающие коэффициенты со сжатым диапазоном: ухудшают оценку, но не обнуляют её.
4.	K_охвата — повышающий коэффициент точки замера, диапазон 1,0–2,0, база 1,0 (низкий трафик): коэффициент только повышает оценку, что сохраняет сопоставимость QualityScore между точками. Источник значений — два этапа: MVP — статические данные, предоставленные отделом маркетинга, заносятся в справочник точек замера (отдел маркетинга коэффициентами в системе не управляет); этап развития — динамическая оценка: K_охвата рассчитывается из трафика в кадре (автомобили, общественный транспорт, пешеходы).
5.	Сторона движения (своя/встречная) для каждой конструкции задаётся атрибутом в справочнике (точки замера контролируемые), из видео вычисляется только смещение от центра кадра.
6.	Хранение: по каждой детекции сохраняются все сырые и нормированные значения метрик отдельно от итоговой оценки (см. «Описание полей и шкал»). Итоговая оценка пересчитывается поверх сохранённых данных.
7.	Фильтр достоверности: детекции с уверенностью модели ниже порога (по умолчанию 0,6) помечаются флагом «низкая достоверность» и исключаются из итоговой выборки (порог настраивается администратором). Уверенность модели в формулу оценки не входит.
8.	Протокол замера: для каждого замера фиксируются направление, полоса, время суток, погодные условия — для корректного сравнения динамики между датами.
9.	Приватность: лица, госномера ТС и иные ПДн, попадающие в кадр, в результатах и интерфейсе не отображаются.

Схема процесса
Видео с точки замера → Детекция (модель CV) → Сырые метрики по конструкции
→ E = время в кадре (сек, сырое) × балл площади
→ E × K_положения × K_контраста = QualityScore
→ × K_охвата (справочник точек) = VisibilityScore
→ Сохранение в БД → Отчёт пользователю

Обновление K_охвата в справочнике → Пересчёт без повторной обработки видео
Юзер-стори
1. Администратор вносит коэффициент охвата точки замера по данным маркетинга
Описание	Администратор в админке открывает справочник точек замера и вносит/изменяет коэффициент охвата для точки в диапазоне 1,0–2,0 на основании статических данных отдела маркетинга. Отдел маркетинга коэффициентами в системе не управляет.
Роль	Администратор
Триггер	Появилась новая точка замера, либо отдел маркетинга предоставил обновлённые данные по трафику
Предусловие	Администратор авторизован; точка замера заведена в справочнике
Базовый путь	1. Администратор открывает справочник точек замера.
2. Выбирает точку.
3. Указывает коэффициент охвата (1,0 / 1,2 / 1,5 / 2,0) по данным маркетинга.
4. Сохраняет.
5. Система предлагает пересчитать VisibilityScore по всем замерам этой точки.
6. Администратор подтверждает — система пересчитывает оценки поверх сохранённых метрик без повторной обработки видео.
Альтернативные сценарии	АС1. п.3. Введено значение вне диапазона 1,0–2,0 — система выводит ошибку валидации.
АС2. п.6. Администратор отказывается от пересчёта — новый коэффициент применяется только к будущим замерам.
Постусловие / Результат	Коэффициент сохранён; оценки актуальны либо помечены как требующие пересчёта.
2. Пользователь просматривает результаты оценки видимости
Описание	Пользователь просматривает список конструкций с итоговой оценкой и разложением по компонентам (экспозиция, модификаторы, охват), используя фильтры по точке замера, дате, бренду.
Роль	Пользователь (аналитик/менеджер)
Триггер	нет
Предусловие	Пользователь авторизован; есть обработанные замеры
Базовый путь	1. Система открывает отчёт со списком конструкций.
2. Пользователь фильтрует по точке, периоду, бренду.
3. Открывает карточку конструкции — видит разложение оценки по компонентам и условия замера.
4. Детекции с флагом «низкая достоверность» отображаются отдельно с пометкой.
Альтернативные сценарии	АС1. Нет данных — система выводит фильтры и шапку таблицы. Ниже текст: нет данных.
АС2. Ошибка — система выводит сообщение «Что-то пошло не так» и предлагает попробовать снова.
Постусловие / Результат	Пользователь закрывает отчёт или меняет фильтры.
